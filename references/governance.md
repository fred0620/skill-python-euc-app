# 治理：只留大架構

## 原則

- 開發者通常不是資安負責人，也不知道每間公司的制度。寫太細的規範（風險分級矩陣、EUC 登記編號、資料分級）反而沒人填得了。
- 所以只留**一定要做的事**和**交接需要的資訊**，政策面一律寫「公司另有規定時以公司為準」。
- 治理盡量自動化：能讓 CI 擋的就不要靠人記得。

## 每個專案固定的文件

| 檔案 | 給誰 | 內容 |
|---|---|---|
| `README.md` | 所有人 | 一句話用途、怎麼用、該看哪份文件 |
| `OWNER.md` | 負責人、主管 | 用途、負責人與備援人、程式碼位置、處理什麼資料、出問題怎麼辦、怎麼停用。一頁就好 |
| `CHANGELOG.md` | 使用者 | 每一版改了什麼，用使用者看得懂的話 |
| `docs/user-guide.md` | 使用者 | 安裝、操作、常見問題，配截圖 |
| `docs/update-guide.md` | 使用者 | 解除封鎖、更新、退回、手動更新，配示意圖 |
| `docs/design.md` | 接手的人 | 為什麼這樣做。改變決策時更新 |
| `docs/maintain.md` | 接手的人 | 建環境、測試、發版、升級套件。照做一次就能發版 |
| `docs/security-checklist.md` | 發版的人 | 8 項發版前一定要確認的事，其中 4 項自動 |

最容易被忽略的是**備援人**：至少一位同事看過一次發版流程，文件才算被驗證過。

## 版本號

| 改了什麼 | 版本 |
|---|---|
| 修錯、小調整 | 第三碼 +1 |
| 新功能，舊資料照樣能用 | 第二碼 +1 |
| 舊資料要重做，或操作方式大改 | 第一碼 +1 |

存在 `workspace` 的檔案（設定、範本）要有版本欄位，新版要能讀舊格式；比程式還新的格式要擋下來並提示更新。

## CI（GitLab）

| 時機 | 做什麼 |
|---|---|
| 每次 push | `uv lock --check`、測試、`pip-audit`（只提醒） |
| 每月排程 | 同上，弱點檢查失敗會亮紅燈 |
| 打標籤 `vX.Y.Z` | 測試與弱點檢查都要過；檢查標籤＝版本、CHANGELOG 有這一版；打包（含 Windows 離線套件）；上傳並建立 Release |

一次性設定：

- 保護 `v*` 標籤，只有 Maintainer 能建立，等於只有負責人能發布。
- 設每月排程。
- 使用者給 Reporter 權限才看得到 Releases 頁。
- 公司要用內部映像檔或 PyPI 鏡像時，設 `UV_IMAGE`、`UV_DEFAULT_INDEX`。

## 例行節奏

| 頻率 | 做什麼 |
|---|---|
| 每月 | 看排程的弱點檢查，有弱點就升級並發修正版 |
| 每半年 | 升級全部套件與 uv；確認 OWNER.md 正確、還有人在用 |
| 交接時 | 新負責人照維護手冊做一次，在備援人陪同下發布一次 |

## 出事時

1. 使用者先 `run.bat rollback`，回報版本號與 `workspace/logs/app.log`。
2. 結果可能有誤時，通知所有人暫停，改回人工作業。
3. 修正後發新版；要回到舊行為就 revert 後發新版號。

## 怎麼跟主管或 IT 說明

把工具定位成「受管理的 EUC 工具」，不是「繞過 IT 的軟體」：

- 只在本機執行，不連外、不寫入公司系統。
- 程式碼在公司 GitLab，有版本紀錄、測試、弱點檢查。
- 有負責人與備援人，有停用方式。
- 公司有 EUC 或工具登記制度時，照著登記即可。
